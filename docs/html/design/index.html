Tasq Architecture

Issue management and agent orchestration are separated into two SQLite-backed services. UI clients use the issue-tracker as the only user-facing API.

MVP slice: issue-tracker + orchestrator boundary

Service Dependency Map

web-ui

Next.js operational UI.

  • Calls issue-tracker only
  • Shows issues and latest runs

tui

Go terminal UI.

  • Calls issue-tracker only
  • Supports watch mode

issue-tracker

Source of truth for issue state and display aggregation.

  • SQLite: issues, comments, projects, workspaces
  • Owns issue CRUD, status changes, and summaries
  • Serves issue data to UI, TUI, CLI, and orchestrator clients
UI/TUI -> issue-trackersummary, issue CRUD, status updates
orchestrator -> issue-trackerfetch issues and issue states

orchestrator

Source of truth for run state and runner diagnostics.

  • SQLite: runs, runner events, workspace metadata, setup failures
  • Prepares per-issue workspaces
  • Exposes optional loopback runtime inspection APIs

future agent/workspace

Codex app-server and isolated git workspaces.

  • JSON-RPC agent protocol
  • Parallel workspace execution

State Ownership

State Owner Notes
Issue title, body, priority, status issue-tracker User-facing source of truth.
Run records and attempts orchestrator Stored in the orchestrator runstore.
Rendered dashboard web-ui/tui No direct orchestrator calls.

Execution Sequence

1. Ready issue User moves an issue to an active state in the issue-tracker.
2. Fetch issue Orchestrator reads candidate issues and current issue states through the issue-tracker API.
3. Run record Orchestrator stores a run in its SQLite database and records runner events as diagnostics.
4. Runtime API The optional loopback API reads active runs and recent runner events from the runstore.
5. Summary Issue-tracker continues serving issue summaries to web-ui and tui from its own issue data.
