# 共通の監視・委譲手順

`SKILL.md` のサービス状態確認を通過してから読む。すべての操作で選択済みの CLI を使う。以下の `<cli>` は表記上の置換箇所で、シェル変数ではない。コメントの author は環境別の参照に従う。

## 課題の割り当て

1. 会話で指定済みの監視間隔を使う。未指定なら秒数を確認する（既定30秒）。プロジェクトの `WORKFLOW.md` と、該当する `tasq-cli` のコマンド参照を読む。
2. 環境に合った管理可能な監視手順で `<cli> issue watch --interval <seconds>` を起動する。停止要求または阻害要因を報告するまで続け、キューが空でも完了扱いにしない。
3. `issue-ready` ごとに `<cli> issue get <id>` で取得する。委譲前にサービスの前提、最新の `ready` 状態、依存関係を考慮したキューでの実行可否、既存の作業エージェントを再確認する。backlog を自動で ready にしない。
4. 実行中・待機中のIDだけを保持する。読み取り・再起動をまたぐ重複を抑止し、実行枠が埋まっている間は待機IDを保持する。枠が空いたら再確認して割り当てる。結果処理と課題更新が終わった場合や実行対象でなくなった場合はIDを解放する。後日の ready イベントでは再委譲できる。
5. 課題の説明とプロジェクトの手順を渡して委譲する。成功したら `in_progress` に更新し、担当名を進捗コメントに残す。必須レビューのための実行枠を確保・解放する。レビュー待ちの作業エージェントはいったんターンを終了し、レビュー後に再開できる。
6. 監視と並行して委譲先の完了を処理する。失敗や引き継ぎ事項は課題に記録する。監視ターンを終了した後も無人でイベントを処理するかのように伝えない。

## 指定がない場合の委譲先作業手順

プロジェクトの手順に規定がない部分だけを補う。

1. 範囲を確認し、origin を取得して、最新の既定ブランチから専用の新規ブランチ・ワークツリーを作成する。命名はリポジトリ規則を優先し、指定がなければ `<project_root>/.worktrees/tasq/<id>-<summary>` を使う。古い、または他者のワークツリーを再利用しない。ブランチとパスを進捗コメントに記録する。
2. 目的に絞って変更し、適切に検証する。対象部分の指示を読み、無関係な変更を保持する。コミット、既定ブランチへの追従、レビュー、push、PR 作成はリポジトリ規則に従う。
3. PR が存在したら、タイトル・URL・検証・レビュー結果を引き継ぎコメントに記録する。`<cli> artifact set <id> --type pull_request <url>` を登録し、課題を `review` にする。
4. 調査の結果修正が不要なら、手順を満たすためだけの変更や空の PR を作らない。範囲・根拠・検証を記録して結果を報告し、ユーザーまたはプロジェクトで合意した変更なしの場合の完了方針を使う。
5. PR の存在と review 状態を確認し、リポジトリの安全確認が許す場合だけ、自分の作業用ワークツリー・ブランチを削除する。それ以外は保持し、未マージのブランチを強制削除しない。
6. 阻害要因がある場合はコメントを残して `blocked` にし、ワークツリーを保持する。この監視側のサービス競合を、委譲済みの全課題の失敗と解釈しない。

ユーザーの依頼やプロジェクトの要件がない限り、課題の範囲を超える独立した報告書などの成果物を増やさない。課題コメントで要件を満たすなら、調査根拠はそこに記録する。

## イベント形式と復旧

`issue watch` は `--output` を無視し、NDJSON を出力する。

- `type=event`、`eventType=issue-ready`: `body` に課題全体がある。`body.id` を使う。
- `type=error`: `body` の一時エラーを報告し、監視処理自体の再試行を待つ。
- `type=info`: 情報通知。`--verbose` の場合だけ出力する。

完成した行を1回ずつ解析し、未完の行を保持する。標準エラーをイベントとして解析しない。`--seen-ttl` は監視間隔より大きくする（既定900秒）。

予期せぬ終了は報告する。監視要求が継続中で原因が回復可能な場合だけ、サービスの前提を再確認して再起動する。実行中・待機中IDを維持し、短時間の再試行を避ける。権限・設定エラーでは再起動を繰り返さず、阻害理由を報告する。

## 停止

`stop` または同等の中止要求では即座に新規割り当てを止め、自分の監視だけを管理ツール経由で終了して確認する。必要な未読イベントの根拠は保持する。実行中の委譲先と課題・ワークツリーを報告する。監視停止だけでは委譲先の中止や成果物削除の許可にはならない。
