Symphony Service Specification

This single-page guide explains the architecture, scheduling loop, state ownership, workspace safety, agent integration, and conformance surface described in docs/symphony/SPEC.md.

Source: docs/symphony/SPEC.md Status: Draft v1 Generated: 2026-05-31 Audience: implementers and reviewers HTML guide index

Overview

Primary job Poll eligible tracker issues, create isolated workspaces, and run a coding-agent session.
Policy lives in repo WORKFLOW.md provides runtime settings and the prompt template.
One scheduler authority The orchestrator owns in-memory dispatch state, retry state, and live session metadata.
Agent runs are isolated Each issue maps to a sanitized workspace path under the configured workspace root.
Tracker writes are a boundary Symphony schedules and reads tracker state; ticket writes are normally agent/tool work.
Recovery is pragmatic Restart recovery is tracker/filesystem-driven, not durable scheduler-state recovery.

Runtime Flow

A tick always reconciles active runs before dispatch. If configuration is invalid, new dispatch is skipped but the service stays alive where possible.

01
Startup

Configure logging, watch workflow, validate config, clean terminal workspaces.

02
Poll Tick

Run reconciliation, validate dispatch config, fetch active candidates.

03
Eligibility

Filter claimed/running issues, blockers, active/terminal state, and slot limits.

04
Dispatch

Claim issue in memory, create worker, prepare workspace, build prompt.

05
Agent Turns

Run first prompt and continuation turns on the same live thread up to max turns.

06
Exit / Retry

Release running entry, update metrics, schedule continuation or failure backoff.

Dispatch Eligibility

  • Issue has required identity fields: id, identifier, title, and state.
  • Issue state is active and not terminal.
  • Issue is not already running, claimed, or retry-queued.
  • Global and per-state concurrency slots are available.
  • Todo blockers are terminal, otherwise dispatch is held.

Contracts

Workflow contract

WORKFLOW.md has optional YAML front matter and a strict prompt template. Config changes must reload without crashing the service.

tracker:
  kind: linear
  api_key: $LINEAR_API_KEY
  project_slug: example
polling:
  interval_ms: 30000
workspace:
  root: ~/symphony_workspaces
Tracker contract

The scheduler requires candidate fetch, state refresh by id, and terminal-state fetch for cleanup. Linear is the spec version's concrete adapter.

fetch_candidate_issues()
fetch_issues_by_states(state_names)
fetch_issue_states_by_ids(issue_ids)
Agent runner contract

Start the Codex app-server in the per-issue workspace, render a strict prompt, stream events, and fail attempts on protocol or timeout errors.

workspace -> prompt -> app-server session
first turn: rendered issue prompt
continuation: same thread + short guidance
Observability contract

Structured logs are required. Runtime snapshot, dashboard, and JSON API are recommended or optional surfaces, not correctness dependencies.

issue_id=... issue_identifier=...
session_id=...
action=dispatch outcome=completed

Safety and Failure Handling

MUSTWorkspace cwd

The coding agent must launch with cwd == workspace_path.

MUSTRoot containment

Resolved workspace path must remain under resolved workspace root.

MUSTSanitized key

Workspace names allow only [A-Za-z0-9._-]; all else becomes _.

SHOULDSecret handling

Resolve secrets through env indirection and never print token values.

SHOULDHook safety

Run hooks with timeouts and truncate noisy output in logs.

SHOULDHarness hardening

Document approval, sandbox, network, and credential posture for the deployment.

Key risk: a permissive deployment can expose repository data, tracker data, credentials, or host filesystem state to an agent. The spec intentionally leaves approval and sandbox posture implementation-defined, so every implementation must document its own safety model.
Failure classExpected recovery
Workflow/configSkip new dispatch, keep service alive where possible, continue reconciliation.
Workspace/hookFail current attempt and let orchestrator schedule retry.
Agent sessionMap to normalized error, stop session, schedule backoff retry.
Tracker candidate fetchSkip dispatch for the tick and retry next tick.
Reconciliation refreshKeep active workers running and retry refresh later.
Dashboard/log sinkDo not crash orchestrator; surface warning through remaining sink.

Tasq Deviations

Tasq uses the Symphony specification as direction, but intentionally keeps the local issue-tracker service as the tracker adapter boundary.

Tasq does not currently implement the Linear tracker client in the spec. It maps the tracker boundary to its local issue-tracker API, preserving issue ownership and lease-backed work-item claims in the existing service boundary.

Definition of Done Themes

  • Required: workflow loading, validation, scheduling, workspace safety, tracker reads, agent launch, structured logs, and failure recovery.
  • Recommended: status dashboard/API, real integration profile, stronger harness hardening, and richer observability.
  • Deployment-specific: approval posture, sandbox strictness, workspace population, and external isolation.
