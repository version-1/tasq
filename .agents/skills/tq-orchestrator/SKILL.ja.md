# 目的

ready の課題を監視し、解決を委譲する。親は監視と引き継ぎを管理し、自身では課題を解決しない。既定の作業手順よりプロジェクトの `WORKFLOW.md` を優先する。

# 最初に orchestrator の稼働を確認する

監視間隔の質問、監視の起動、作業エージェントの作成、課題の変更より先に、次を実施する。

1. ユーザー指定の CLI を選ぶ（既定は `tq`、指定時は `tqdev`）。以降の操作では同じプロファイル、`TQ_HOME`、API 接続先を維持する。`<cli> --output json service status`（`tq service status` の JSON 形式）を実行する。
2. `orchestrator` サービスの項目を確認する。コマンドが成功し、項目がちょうど1件あり、明示的に `state: stopped` の場合だけ続行する。`running` ならこのスキルは利用不可として、競合を報告して終了する。監視・委譲を始めず、サービスも自動停止しない。
3. コマンド失敗、項目の欠落・重複、未知の状態では、前提を確認できないと報告して終了する。情報の欠落を停止扱いにしない。API 接続先がリモート、またはローカルサービスのプロファイルと異なる場合、ローカルの状態確認では不十分である。同じ接続先の状態を確認できるまで開始しない。

監視の再起動前と各課題の新規委譲前にも同じ確認を行う。別の orchestrator が起動した場合や状態を確認できなくなった場合、新規割り当てと自分の監視を停止し、実行中の委譲先は保持して状況を報告する。この確認は競合を減らすもので、別エージェントによる同時起動を防ぐ排他ロックではない。

# 手順の選択

前提を満たしたら、共通手順の [default.ja.md](references/default.ja.md) を読み、実行環境に合う参照だけを追加で読む。

- Claude Code: [claude.ja.md](references/claude.ja.md)。
- Codex: [codex.ja.md](references/codex.ja.md)。
- その他の環境: 管理可能な監視ツールとサブエージェント機能がある場合だけ共通手順を使う。なければ不足する機能を報告し、開始しない。
