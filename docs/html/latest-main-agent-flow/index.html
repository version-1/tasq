Tasq / Symphony Orchestrator

Launching agents from latest main, assigning work, and reaching completion

This diagram describes the implementation visible on the latest fetched origin/main. The orchestrator polls the issue tracker for ready work, prepares a per-issue workspace from the configured source, queues a run, dispatches it to CodexRunner, streams runner events into SQLite, and marks the run terminal when the agent returns.

Scope: cmd/orchestrator Runtime: internal/orchestrator/coordinator Agent: codex app-server Store: runs + runner_events

Overview

Source of work Poller.Poll reads issues in ready state from the issue-tracker API.
Workspace basis workspace.source defaults to the directory containing WORKFLOW.md. To run from latest main, point the orchestrator at a latest-main checkout as this source.
Assignment unit The queue record is a run row with issue_id, workspace path, attempt, and orchestrator ID.
Dispatch gate Dispatcher.Dispatch starts queued runs while running + claimed stays below the configured maximum.
Agent protocol CodexRunner launches bash -lc codex app-server in the workspace and uses JSON-RPC over stdio.
Completion signal A matching turn/completed notification allows the runner to return succeeded; errors and cancellations become terminal run statuses.

Architecture

The main process wires the workflow config, issue tracker client, workspace manager, dispatcher, poller, and optional HTTP status surface. The runtime boundary is explicit: tracker state is read through the API, run state is local SQLite, and agent execution is isolated to a per-issue workspace.

Gaps and Notes

Latest-main workspace freshness is indirect in the implementation. workspace.source is copied into the per-issue workspace, excluding .git, .worktrees, and node_modules. If that source directory is a checkout at latest main, the agent starts from latest main content; the orchestrator itself does not run git fetch or git checkout main for each workspace.
