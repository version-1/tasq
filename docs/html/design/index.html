Tasq Architecture and Runtime Boundary

Tasq separates user-facing issue state from orchestration runtime state. The issue-tracker is the stable API for UI, TUI, CLI, and reconciliation. The orchestrator owns run records, runner events, workspace metadata, and optional loopback inspection.

issue-tracker owns issue data orchestrator owns run data clients avoid direct orchestrator coupling workspace and runner are runtime boundaries Generated: 2026-06-15 HTML guide index

Overview

The design keeps issue management, run orchestration, and agent execution as separate ownership areas. This lets humans and agents share one issue API without making UI clients depend on transient runner state.

User-facing API web-ui, tui, and tq use issue-tracker as the primary API boundary.
Runtime state orchestrator stores runs, events, workspaces, and setup failures in its own SQLite database.
Local-first data service state lives under local SQLite databases and files beneath TQ_HOME.
Agent boundary future Codex app-server work is isolated behind runner and workspace manager responsibilities.

Structure

The repository keeps command entry points, issue domain code, and orchestration runtime packages separated. The HTML view is intentionally static; the source files below are the durable references.

Command entry points

  • cmd/issue-tracker - user-facing API service
  • cmd/orchestrator - run orchestration process
  • cmd/tq - CLI wrapper around issue-tracker API
  • cmd/tasq-tui - terminal UI client
  • cmd/web - Go web server and React frontend

Internal ownership packages

  • internal/issue
    • api, domain/entity, store
  • internal/orchestrator
    • coordinator, runner, runstore, workspace, workflow
  • internal/cli/tq - CLI command behavior

Flow

The orchestration path is intentionally read-through from issue-tracker and write-through to orchestrator runstore. Issue status is not mutated directly by the orchestrator.

Issue becomes actionable A user or agent updates issue status through issue-tracker APIs or tq.
Orchestrator reconciles The orchestrator reads candidate issues and workflow configuration.
Workspace is prepared A sanitized per-issue workspace is created and metadata is persisted.
Runner executes Future Codex app-server work reports progress as runner events.
Inspection stays local Run records and diagnostics are exposed by optional loopback APIs.

State Ownership

issue-tracker Issue state

Issue state is user-facing and belongs to the tracker database. The orchestrator reads it but does not directly mutate it.

backlog ready in_progress review done blocked failed

orchestrator Run state

Run state is operational history and diagnostics. It stays in the orchestrator runstore with runner events and workspace metadata.

queued running succeeded failed cancelled
State / artifact Owner Storage Mutation path
Issue title, body, priority, status, assignee issue-tracker SQLite issue database Issue API, tq, UI, TUI
Comments and attachment metadata issue-tracker SQLite + files under TQ_HOME Comment and attachment APIs
Run records, attempts, runner events orchestrator orchestrator SQLite runstore Coordinator and runner boundary
Workspace metadata and setup failures workspace orchestrator SQLite runstore Workspace manager

API Surface

The issue-tracker is the current stable user-facing API. Orchestrator HTTP is loopback/runtime inspection, not the main client contract.

Issue-tracker endpoints

Area Representative endpoints
Health + summary GET /api/v1/health, GET /api/v1/summary
Projects GET/POST /api/v1/projects, workflow check and override APIs
Issues GET/POST /api/v1/issues, PATCH /api/v1/issues/{id}, POST /api/v1/issues/states
Comments + attachments POST /api/v1/issues/{issueId}/comments, attachment upload/content/delete APIs

Response and CLI contract

Contract Shape
Success JSON { "data": ..., "meta": {} }
Error JSON { "error": { "code": "...", "message": "..." }, "meta": {} }
CLI default Human-readable text for terminals
CLI tools --output json for agents and scripts

Operations

Local development has two supported shapes: Docker Compose in one long-lived dev container, and host-only services through tq.

Compose development make dev-up starts OpenAPI UI plus issue-tracker, orchestrator, and web in the dev container.
Host-only services tq service start runs tracker, orchestrator, and web on fixed local ports 37651-37653.
Migrations first Run tq migrate or make run-migrate before starting services when migrations are pending.
Verification Command What it protects
Go tests go test ./... Backend domain, stores, API handlers, orchestration packages
Web build cd cmd/web/frontend && npm run build React production build and frontend integration
Web typecheck cd cmd/web/frontend && npm run typecheck TypeScript contracts and component usage

Risks / Open Questions

Tracker sync boundary External tracker sync is still an open decision: issue-tracker ownership vs provider interface.
Transcript storage Large full-fidelity Codex transcripts may need filesystem artifacts instead of SQLite rows.
Production exposure Authentication, authorization, and network exposure are explicitly out of the current MVP scope.
