# 目的

Tasq の Issue Tracker から ready の課題を監視し、プロジェクトのワークフローに従うサブエージェントへ各課題を割り当てる。

# 制約

- オーケストレーターは課題の解決を必ずサブエージェントへ委譲し、自身では解決しない。
- プロジェクトの `WORKFLOW.md` を優先する。プロジェクトのワークフローに規定がない場合に限り、後述の既定ワークフローを適用する。

# 監視と割り当て

1. 会話内で指定済みでなければ、監視間隔を秒単位でユーザーに確認する（既定値: 30）。
2. **Monitor ツール**があれば使用し、なければ後述の管理可能なバックグラウンドセッション手順を使用する。ユーザー指定の CLI（例: `tqdev`）で `tq issue watch --interval <seconds>` を実行する。以降の issue・comment・artifact 操作も同じ CLI と API 接続先を使用する。
3. `issue-ready` イベントを受信するたびに、`body.id` から課題IDを読み取り、`tq issue get <issue_id>` で課題を取得する。
4. プロジェクトの `WORKFLOW.md` に従い、規定されていない部分だけを後述の既定ワークフローで補って、課題をサブエージェントへ割り当てる。
5. 割り当てに成功したら、次の処理を行う。
   - `tq issue update <issue_id> --status in_progress` で課題の状態を `in_progress` に変更する。
   - `tq comment add <issue_id> --author claude-code --body "<comment>"` でサブエージェント名を記録する。

# Monitor がない環境での監視

管理可能なバックグラウンドコマンドセッションがあれば、Monitor がなくても実行できる。

1. プロセス実行中に永続的なセッションIDを返すコマンド実行ツールで、watch を1回起動する。Codex では短い `yield_time_ms` を指定した `exec_command` を使用し、返された `session_id` を保持する。Ctrl-C の送信に必要なら `tty: true` を指定する。起動前に標準出力と標準エラーを専用の一時スプールディレクトリ内の別ファイルへリダイレクトし、ディレクトリをセッションIDとともに保持する。このコマンドは意図的に常駐する。`nohup`、追跡しないシェルの `&`、破棄される非同期ツール呼び出しで切り離さない。
2. 同じセッションの `write_stdin` で稼働状況を確認し、保持したバイト位置から標準出力のスプールを読む。ユーザーの入力、作業エージェントの完了、停止要求に対応できるよう、1回の待機は最大30秒とする。出力やキューが空でも完了扱いにせず、委譲先の状況を確認しながら監視を続ける。管理可能なセッションツールもない場合は不足する機能を報告し、開始済みとは伝えない。
3. バイト位置を管理する読み取り処理で、スプールの完成した NDJSON 行を直接解析し、末尾の未完の行は次回へ持ち越す。ツールの表示出力は切り詰めや PTY による標準出力・標準エラーの混在があるため、イベント源として解析しない。読み取り処理はイベント種別・課題ID（全文は後で取得）と長さを制限した error/info 要約だけを件数制限付きで返し、応答が欠けずに届いた後だけバイト位置を進める。応答が切り詰められたら前回位置から件数を減らして再読する。完成済み行の解析に失敗したら報告し、依存関係を考慮するキューと照合してから再開する。標準エラーは別のスプールファイルに保持する。`type=event` / `eventType=issue-ready` のみを割り当て対象とし、`error` は報告して watch 自体の再試行を待つ。`info` は通知として扱う。
4. 委譲前に最新の課題を取得し、依存関係を含め ready かつ実行可能であることを確認する。現在実行中・待機中の課題IDだけをローカルで保持し、読み取りや再起動をまたぐ重複を抑止する。委譲先の結果処理と tracker 更新が完了した場合、または待機中の課題が実行対象から外れた場合はIDを解放する。同じIDで後日 ready イベントが来たら、最新状態と実行中エージェントの不在を確認して再委譲できる。サブエージェントの実行枠を守り、枠が空くまで待機IDを保持し、割り当て直前に再確認する。backlog の課題を自動で ready に変更しない。
5. 監視を続けながら委譲先の結果を処理し、引き継ぎ手順を実施する。エージェントが作成するコメントの author は実行元に合わせる（Codex では `codex`、Claude Code では `claude-code`）。後述のコマンド例も必要に応じて置き換える。
6. watch が予期せず終了したら終了を報告し、監視要求が継続中で原因が回復可能な場合のみ再起動する。実行中・待機中のIDを維持して課題の最新状態を再確認し、短時間の再試行ループを避ける。権限・設定エラーでは再起動を繰り返さず阻害理由を報告する。`--seen-ttl` を指定する場合は監視間隔より大きくする。
7. `stop` または同等の中止要求を受けたら即座に新規割り当てを止め、自分が起動した watch セッションへ Ctrl-C を送信し、終了を確認する。受信済みイベントの処理状況をすべて確認するまでスプールを保持し、復旧に必要ならパスを報告する。稼働中の委譲先と課題・ワークツリーを報告する。監視停止だけでは作業エージェントのキャンセルや成果物削除の許可を意味しない。管理不能な watcher を残さず、監視ターンを終了して無人のセッションがイベント処理を継続するかのように伝えない。

# 委譲後の既定ワークフロー

1. 課題のタイトルと説明から作業範囲を確認する。
2. 編集前に、最新のデフォルトブランチを基点とする専用ブランチとワークツリーを作成する。
   - `git fetch origin` を実行する。
   - `origin/main` またはリポジトリのデフォルトブランチから作業ブランチを作成する。
   - `<project_root>/.worktrees/tasq/<issue_id>-<issue-summary-title>` にワークツリーを作成する。
   - `tq comment add <issue_id> --author claude-code --body "<comment>"` でワークツリー名とブランチ名を記録する。
3. 課題を満たす変更に絞って実装する。最小限の有効な検証から始め、共有部分に影響する場合は検証範囲を広げる。
4. 変更をコミットし、Pull Request を作成または更新する。
5. Pull Request を用意できたら、次の処理を行う。
   - `tq comment add <issue_id> --author claude-code --body "<comment>"` でタイトルと URL を記録する。
   - `tq artifact set <issue_id> --type pull_request <pr_url>` で URL を artifact として登録する。
   - 未解決事項や引き継ぎ事項があればコメントを残す。
   - `tq issue update <issue_id> --status review` で課題の状態を `review` に変更する。
6. Pull Request が存在し、課題が `review` になっていることを確認してから、作業用のワークツリーとブランチを削除する。それ以外の場合はワークツリーを保持する。

エラーやコマンド実行権限の不足など、何らかの理由で課題を完了できない場合は、次の処理を行う。

1. `tq comment add <issue_id> --author claude-code --body "<comment>"` で阻害理由を説明する。
2. `tq issue update <issue_id> --status blocked` で課題の状態を `blocked` に変更する。
3. 後続対応のため、作業用のワークツリーを保持する。

# 出力プロトコル

> [!NOTE]
> `tq issue watch` は実験的なコマンドであり、CLI の他の機能から意図的に分離されている。

`tq issue watch` はグローバルの `--output` フラグを無視し、常に1行につき1個の JSON オブジェクトを出力する。Monitor では標準出力の各行が通知1件になる。バックグラウンドセッションでは、前述の手順で完成した行を順次処理する。

- `{"type":"error","body":"<message>"}` — 一時的な監視エラー。ループは継続する。
- `{"type":"event","eventType":"issue-ready","body":<issue>}` — ready の課題。`body` に課題の全データが含まれる。
- `{"type":"info","body":"<message>"}` — 起動設定または監視結果の概要。`--verbose` を指定した場合のみ出力する。

フラグ:

- `--interval <seconds>`: 監視間隔（既定値: 30）。
- `--seen-ttl <seconds>`: 同じ課題のイベントを再出力しない期間（既定値: 900。`--interval` より大きい値が必要）。
- `--verbose`: info エンベロープを出力する。

ループは SIGINT、kill、監視ツール・セッションのタイムアウトのいずれかで停止されるまで継続し、自動では終了しない。
