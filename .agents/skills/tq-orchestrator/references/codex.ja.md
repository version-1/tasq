# Codex の設定

Codex 内で、共通のサービス状態確認を通過した後に使う。コメントの author は `codex`。作業とレビューには Codex の連携ツールを使い、モデル・役割はリポジトリの指示に従う。

Monitor があれば使用し、なければ以下の管理可能なバックグラウンドセッション手順を使う。常に `default.ja.md` の割り当て・復旧・停止規則も適用する。

1. プロセス実行中に永続的なセッションIDを返すコマンド実行ツールで、watch を1回起動する。Codex では短い `yield_time_ms` を指定した `exec_command` を使用し、返された `session_id` を保持する。Ctrl-C の送信に必要なら `tty: true` を指定する。起動前に標準出力と標準エラーを専用の一時スプールディレクトリ内の別ファイルへリダイレクトし、ディレクトリをセッションIDとともに保持する。このコマンドは意図的に常駐する。`nohup`、追跡しないシェルの `&`、破棄される非同期ツール呼び出しで切り離さない。
2. 同じセッションの `write_stdin` で稼働状況を確認し、保持したバイト位置から標準出力のスプールを読む。ユーザーの入力、作業エージェントの完了、停止要求に対応できるよう、1回の待機は最大30秒とする。出力やキューが空でも完了扱いにせず、委譲先の状況を確認しながら監視を続ける。管理可能なセッションツールもない場合は不足する機能を報告し、開始済みとは伝えない。
3. バイト位置を管理する読み取り処理で、スプールの完成した NDJSON 行を直接解析し、末尾の未完の行は次回へ持ち越す。ツールの表示出力は切り詰めや PTY による標準出力・標準エラーの混在があるため、イベント源として解析しない。読み取り処理はイベント種別・課題ID（全文は後で取得）と長さを制限した error/info 要約だけを件数制限付きで返し、応答が欠けずに届いた後だけバイト位置を進める。応答が切り詰められたら前回位置から件数を減らして再読する。完成済み行の解析に失敗したら報告し、依存関係を考慮するキューと照合してから再開する。標準エラーは別のスプールファイルに保持する。

停止要求またはサービス競合では、自分のセッションへ `write_stdin` で Ctrl-C を送り、終了を確認する。受信済みイベントの処理を確認するまでスプールを保持し、復旧に必要なパスを報告する。実行中の委譲先は `default.ja.md` に従って扱う。
